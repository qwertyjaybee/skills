# Jira Task Description Generation Guidelines (`/jira-description`)

## 1. Overview & Core Philosophy
This skill automates the creation of high-quality, human-friendly descriptions for Jira Kanban tasks based strictly on codebase changes across the project's frontend (`ui/`) and backend (`api/`) repositories.

Descriptions generated by this skill are intended for product owners, QA engineers, designers, and stakeholders. They must explain **what the edits were for** purely through the lens of the product experience:
- **Zero Backend / Code Jargon:** Never include database table names, SQL queries, schema migrations, internal GraphQL query/mutation names, or internal class/service identifiers.
- **Strictly User-Centric 3-Part Output Structure:**
  1. **Description:** High-level narrative summarizing the feature or enhancement, how it functions end-to-end, and the value it delivers to users.
  2. **Requirements:** Granular functional specifications organized under clear functional subheadings, explicitly quoting exact UI headings, button labels, dropdown options, validation limits, confirmation dialogs, and error messages.
  3. **Permissions:** Explicit permission statement accompanied by a standardized 4-column Markdown table detailing permissions, capabilities unlocked, UI application areas, and default roles.
- **Interactive Approval Gate:** The draft description is always presented in an interactive Markdown artifact (`RequestFeedback: true`) for user review before anything is uploaded to Jira.
- **Automated Python Jira Upload:** Upon user approval (clicking **Proceed**), the agent executes the dedicated upload script (`scripts/upload_to_jira.py`) to upload the approved description directly to Jira via the Jira REST API.

## 2. Command Syntax & Mode Parsing

### Invocation Formats
```text
/jira-description <task_name_or_link> <FRD|SED>
```

#### Supported Examples:
- `/jira-description AIRI-284 | Membership UI Redesign to Draggable Hierarchy like Design SED`
- `/jira-description https://company.atlassian.net/browse/AIRI-284 FRD`
- `/jira-description AIRI-284 sed`
- `/jira-description AIRI-284 frd`

### Parsing Rules:
1. **Task Key Extraction:**
   - Extract the Jira issue key using regex: `([A-Z]+-[0-9]+)` (e.g., `AIRI-284`).
   - Supports raw keys (`AIRI-284`), Jira URLs (`https://.../browse/AIRI-284`), or full commit / task title strings.
2. **Mode Extraction:**
   - Matches `\b(FRD|SED)\b` case-insensitively (`SED`, `sed`, `FRD`, `frd`).
   - If the mode is omitted in the prompt, inspect the commit messages for clues or ask the user to clarify whether the task is **SED** or **FRD**.

## 3. SED vs. FRD Mode Rules & Expected Output Structure

### 3.1 Common Output Anatomy
Every generated description must adhere strictly to the following 3-part layout:

```markdown
# [Feature Documentation | Enhancement Documentation]

## Description
[1-2 clear, reader-friendly paragraphs summarizing the feature/enhancement, the user problem it solves, and how it behaves across the platform without technical code jargon]

## Requirements

### [Functional Area 1: Interface & Core Layout]
- Heading: "[Exact Screen Heading]". [Initial screen state and default components].
- Pick a type from [Selector Name] and click [Action Button]: "[Option 1]", "[Option 2]", "[Option 3]".
- The [Panel Name] lists all items with a count. Items can be reordered, selected, and deleted.
- Deleting asks for confirmation ("[Confirmation Modal Title]"). [Boundary/edge conditions]: "[Constraint Message]".

### [Functional Area 2: Form Details & Validations]
- [Field Name] required, up to [X] characters: "[Exact Error Message]".
- [Slug / Code / Input] up to [X] characters, [character restrictions]: "[Exact Error Message]".
- [File / Image Upload] [Allowed extensions] up to [Size Limit]: "[Exact Error Message]".
- [Attribute Controls]: [List of selectors, visibility states, author, tags, and category pickers].
- [Dependent / Conditional Validation]: "[Exact Error Message]". Empty state: "[Exact Empty State Message]".
- Tag / Token input rules: "[Exact Input Helper Text]". Also enforced on save.
- Sidebar / Drawer controls: [Collapsing, expanding, and restoring states].

### [Functional Area 3: Saving, Publishing & Validation Workflows]
- Action buttons: [List of buttons, e.g., Preview, Save Draft / Update as Draft, Submit for Review, Publish Now / Schedule / Update].
- Every item/section is validated before saving. Failing items open with a "[Validation Dialog / Box]"; [Panel Name] displays an error count.
- Items are saved in the exact order shown.
- Media handling: [Allowed formats, file size limits, and exact rejection error message].
- Removed media is deleted on save. Failed save keeps nothing, reverting new uploads.
- Feedback notifications: "[Exact Success Message on Create]" / "[Exact Success Message on Update]", followed by redirection to [Target List Screen].

### [Functional Area 4: Content & Editor Rules]
- Content formatting and sanitization: [Sanitization behavior, e.g., pasted tables converted to paragraphs; text colours, highlights, font sizes, and code formatting stripped].
- Character counters: [Editor counters, e.g., WYSIWYG Editor shows "count/10000", turning red at the limit; images excluded from count].
- Input limits: Typing halts at limit; pasted text is truncated at the limit.

### [Functional Area 5: Listing & Data Views]
- Layout: [Card / Table layout with exact header labels, action buttons, and search placeholder text: "Search..."].
- Loading placeholders on desktop and mobile views.
- Error handling: "[Exact Failure Message]".

### [Functional Area 6: Public / Consumer Display]
- Responsive typography and wrapping: Long text wraps cleanly without overflowing containers or breaking viewport boundaries.

## Permissions
[Summary sentence, e.g., "No new permissions. Uses the existing [Module] permissions:" OR "Introduces new permissions for [Module]:"]

| Permission | Allows the user to | Where it applies | Default roles |
| :--- | :--- | :--- | :--- |
| `permission-slug` | [Capability explanation] | [UI screen, panel, or button] | [Default assigned roles] |
```

---

### 3.2 SED Mode (System Enhancement)
- **Applicability:** Enhancement, optimization, or refinement of an existing feature or workflow.
- **Tone & Perspective:** Explains how existing pain points or friction were eliminated and how the workflow was streamlined.
- **Title:** `# Enhancement Documentation`
- **Focus:** Highlight what was improved, simplified, or redesigned, followed by the complete categorized requirements and permissions table.

---

### 3.3 FRD Mode (Functional Requirement / New Feature)
- **Applicability:** Pure creation of brand-new capabilities, interfaces, or Version 2 (v2) components.
- **STRICT PURE-CREATION RULE:**
  - **Never use negative, deletion, or deprecation framing** (e.g., do not write "removed pagination", "deleted old component", "deprecated legacy logic").
  - **Always frame constructively:** Describe changes as new capabilities introduced.
    - *Example (Bad):* "Removed pagination in membership tier component."
    - *Example (Good):* "Introduced a unified single-view list allowing administrators to view and manage all tiers simultaneously without page breaks."
- **Title:** `# Feature Documentation`
- **Focus:** Detail all brand-new end-to-end workflows, section builders, form details, error states, and responsive display.

### 3.4 Canonical Reference Example (Gold Standard)

The following example illustrates the exact structure, quoting discipline, and level of detail expected:

```markdown
# Feature Documentation

## Description
Posts are now built from sections, the same way as Pages. On the Add New Post and Edit Post screens, an editor adds sections from a design template list, puts them in order and fills in each one. All sections save together with the post, in the chosen order, along with any images inside them. The All Posts list has a new card layout and shows loading placeholders. Section editors now remove pasted tables and custom colours, and editors with a limit show a character count.

## Requirements

### Build a post from sections
- Heading: "Add New Post" or "Edit Post". A new post starts with one section, "Main Content Body".
- Pick a type from Design Template and click Add Section: "WYSIWYG Editor", "Hero Banner", "Tabbed Section", "Featured Stories".
- The Page Sections panel lists all sections with a count. Sections can be reordered, selected and deleted there.
- Deleting asks for confirmation ("Delete Section"). The last section can't be deleted: "A page must have at least one content section."
- Existing posts open with their content in sections.

### Post details
- Post Title required, up to 255 characters: "Post title is required".
- Slug up to 60 characters, lowercase letters, numbers and dashes: "Only lowercase letters, numbers and dashes."
- Featured Image SVG, PNG, JPG or GIF up to 5MB: "Featured image must be 5MB or less."
- Post Attributes: Visibility (Public, Private, Password Protected), Password (Password Protected only), Publish Date/Time, Author, Category*, Tags.
- Category* required: "Select at least one category." With none available: "No categories available — add one under Post Categories, or reload if they failed to load."
- Each tag up to 125 characters: "Press Enter to add tags (max 125 characters each)." Also enforced on save.
- The sidebar collapses; "Post Panel" reopens it.

### Saving and validation
- Buttons: Preview, Save Draft / Update as Draft, Submit for Review / Save and Review, Publish Now / Schedule / Update.
- Every section is checked first. A section with a problem opens with a "Required Field / Validation Error" box; Page Sections shows an error count.
- Sections are saved in the order shown.
- Section images: JPG, PNG, WEBP or GIF, 5 MB or smaller, else "Section images must be JPG, PNG, WEBP or GIF and 5 MB or smaller."
- Removed section images are deleted on save. A failed save keeps nothing, including new uploads.
- "Post created successfully!" / "Post updated successfully.", then back to All Posts.

### Editor content rules
- In Hero Banner, Tabbed Section and Featured Stories, pasted tables become paragraphs; text colours, highlights, font sizes and code formatting are removed.
- WYSIWYG Editor, Hero Banner and Featured Stories show "count/10000", red at the limit. Images don't count.
- Typing stops at 10,000 characters; pasted text is cut off at the limit.

### All Posts list
- New card layout: "All Posts", "Manage and publish posts", Add Post, "Search posts...".
- Loading placeholders on desktop and mobile.
- On failure: "An error occurred while loading posts. Please try again."

### Public display
- Long text in hero, tabbed and featured story sections wraps instead of running off the screen.

## Permissions
No new permissions. Uses the existing Posts permissions:

| Permission | Allows the user to | Where it applies | Default roles |
| :--- | :--- | :--- | :--- |
| `create-post` | Create posts and save drafts | Add Post; Save Draft | Super Admin (to confirm) |
| `edit-own-post` / `edit-others-post` | Edit posts | Edit Post; Update as Draft | Super Admin (to confirm) |
| `submit-for-review-post` | Send a post for review | Submit for Review | Super Admin (to confirm) |
| `publish-post` | Publish a post now | Publish Now | Super Admin (to confirm) |
| `schedule-post` | Schedule a post | Schedule | Super Admin (to confirm) |
```

## 4. Codebase & Git Inspection Protocol

To ensure the description accurately extracts exact UI strings, validation errors, and permissions, the agent must inspect changes across both repositories:

1. **Scan UI Commits:**
   ```bash
   git -C /opt/core-aairi/ui log --grep="<TASK_KEY>" --oneline -n 20
   ```
2. **Scan API Commits:**
   ```bash
   git -C /opt/core-aairi/api log --grep="<TASK_KEY>" --oneline -n 20
   ```
3. **Scan Staged / Active Changes:**
   ```bash
   git -C /opt/core-aairi/ui diff --staged --name-status
   git -C /opt/core-aairi/api diff --staged --name-status
   ```
4. **Inspect Exact UI Strings & Validation Messages:**
   - Inspect `.component.html` and `.component.ts` files for button text, headings, dialog messages, and validator error strings (e.g., `Validators.required`, `Validators.maxLength`).
   - Note exact strings in quotes (e.g., `"Post title is required"`).
5. **Inspect Permissions & Authorization:**
   - Check `api/config/permissions.php` and GraphQL schema directives (`@hasPermission`) for relevant permission keys.
   - Check UI permission tags (`<has-permission [permission]="...">`).
   - Populate the 4-column Permissions table accurately: `Permission`, `Allows the user to`, `Where it applies`, and `Default roles`.
6. **Translate Technical Edits into User Impact:**
   - *Example:* Backend added `sort_order` column & reorder mutation -> Translate to: *"Section reordering saves automatically and persists in the order shown."*
   - *Example:* Frontend added TipTap table filter & color stripping -> Translate to: *"Pasted tables become paragraphs; text colours, highlights, font sizes and code formatting are removed."*

## 5. Two-Step Approval & Execution Workflow

### Step 1: Interactive Draft Plan Artifact
1. The agent compiles the drafted description matching the selected mode template.
2. Writes an interactive Markdown artifact:
   - Path: `<appDataDir>/brain/<conversation-id>/jira_description_<TASK_KEY>.md`
   - Set `ArtifactMetadata.RequestFeedback: true`
   - Set `ArtifactMetadata.UserFacing: true`
3. **Mandatory Stop:** Halt execution and wait for the user to review, comment, or click the **Proceed** button.
   - Do NOT attempt to upload to Jira before the user clicks Proceed.

### Step 2: Jira Upload Execution (Always via Python Script)
1. **Mandatory Execution on Proceed:**
   Once the user approves (clicks **Proceed**), the agent **MUST ALWAYS** execute the dedicated Python upload script rather than relying on MCP:
   ```bash
   python3 /opt/core-aairi/.agents/automation/jira-description/scripts/upload_to_jira.py \
     --issue <TASK_KEY> \
     --file <appDataDir>/brain/<conversation-id>/jira_description_<TASK_KEY>.md
   ```
2. **Confirmation:**
   The script outputs the direct issue link upon successful upload:
   ```text
   ✅ Successfully updated Jira issue: <TASK_KEY>
   🔗 Issue URL: https://your-company.atlassian.net/browse/<TASK_KEY>
   ```
   Report this confirmation URL to the user.

3. **Credential Configuration:**
   The script automatically detects credentials in priority order:
   - Config file: `/opt/core-aairi/.agents/automation/jira-description/jira_config.json` (or `~/.gemini/config/jira.json` or `~/.jira_config.json`):
     ```json
     {
       "jira_url": "https://your-company.atlassian.net",
       "jira_email": "your-email@company.com",
       "jira_api_token": "your_jira_api_token"
     }
     ```
   - Environment variables: `JIRA_URL`, `JIRA_EMAIL`, `JIRA_API_TOKEN`.
   - If missing, guide the user to create `jira_config.json` (using `jira_config.example.json` as a template) or export the environment variables.
